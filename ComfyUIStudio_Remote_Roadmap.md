## 0. Принципы, действующие на всю дорожную карту

- **Android никогда не обращается к ComfyUI или Imagine напрямую.** Только к Remote API.
- **Вся логика и все данные — на сервере (ПК пользователя).** Телефон не хранит и не вычисляет ничего, кроме токена подключения и адреса сервера. Это не "native-приложение с REST-клиентом", а **тонкий терминал**, отображающий интерфейс, целиком переданный сервером, без возможности изменить этот интерфейс на стороне телефона.
- **Сначала LAN/личный сервер, полностью и до конца.** Публичное распространение — вопрос, который сейчас сознательно не решается и не проектируется заранее (см. §9).
- **Не дублировать существующую логику.** Remote — новый потребитель `ComfyAPIClient` / бэкенда Imagine, а не копия их кода.
- **Каждая новая зависимость — это тест сборки.** Каждая новая библиотека обязана пройти оба `.spec`-профиля (`-core` и `-full`) и ручную проверку собранного `.exe`.
- **Одноразовый pairing-код ≠ постоянный пароль.** Код живёт минуты, используется один раз, после успешного pairing заменяется на долгоживущий токен устройства.
- **Android никогда не получает произвольный `/prompt`.** Только предметные операции; сырой workflow — вне области MVP.

## 0.1 Архитектурная развилка — РЕШЕНО: вариант B, отдельный пакет

Выбран отдельный пакет `comfyui_studio/remote/`, работающий как собственный процесс — по образцу того, как уже устроен Imagine (`IMAGINE_CLI_FLAG` + self-reinvoke), а не как довесок к бэкенду Imagine.

### Обоснование в контексте решения по §0.3 (см. ниже)

Раз телефон — это терминал, которому *сервер отдаёт готовый интерфейс*, а не только JSON-данные, то Remote-процесс должен уметь отдавать не только API, но и статические страницы/чужие мини-приложения (сейчас — Imagine, в будущем — что-то ещё). Делать это как пристройку к Imagine было бы не совсем логично: Remote — это универсальный шлюз/терминал-сервер, а Imagine — один из "апп", которые через него доступны. Отдельный пакет ложится на эту роль естественнее.

### Реализация (по аналогии с уже существующим `ImagineProcess`/`ImagineLaunchWatcher`)

```
comfyui_studio/remote/
├── __init__.py
├── __main__.py                 # CLI-точка входа: --host/--port/--dev
├── app.py                      # FastAPI-приложение верхнего уровня
├── auth.py                     # проверка Bearer-токена, зависимость FastAPI
├── pairing.py                  # одноразовый код, TTL, попытки
├── device_store.py             # APPDATA-хранилище устройств (hash токена)
├── apps_registry.py            # реестр "апп", доступных терминалу (см. §0.3)
├── routes/
│   ├── system.py               # /api/v1/remote/status
│   ├── pairing_routes.py       # /api/v1/remote/pair/*
│   ├── devices.py              # /api/v1/remote/devices
│   ├── queue.py                # /api/v1/remote/queue
│   ├── apps.py                 # /api/v1/remote/apps
│   └── ws.py                   # /api/v1/remote/ws
└── proxy/
    └── imagine_proxy.py        # реверс-прокси к процессу Imagine (см. §0.3)
```

```
launcher/core/
├── remote_process.py           # RemoteProcess — 1:1 по образцу ImagineProcess
└── remote_watcher.py           # RemoteLaunchWatcher — 1:1 по образцу ImagineLaunchWatcher
```

- `REMOTE_CLI_FLAG` в корневом `main.py`, диспетчеризация до импорта Qt — так же, как `IMAGINE_CLI_FLAG`/`WORKER_CLI_FLAG`.
- `launcher_window.py`: включение Remote — отдельный переключатель в настройках ("Удалённый доступ"), независимый от переключателя интерфейса ComfyUI/Imagine (Remote может понадобиться даже если основной интерфейс — обычный ComfyUI, а Imagine просто один из режимов терминала).
- Жизненный цикл (start/stop/closeEvent) обновляется по тому же паттерну, что уже сделан для Imagine.
- `.spec`-профили: добавить `comfyui_studio/remote` в сборку так же, как `comfyui_studio/imagine` (datas для не-`.py` файлов при их появлении, `collect_all` при необходимости).

## 0.3 РЕШЕНО: модель "терминала" — что это значит на практике

Формулировка: *"вся логика и данные должны оставаться на сервере, а телефон — просто терминал, где пользователь видит интерфейс (пока что только imagine, но с возможностью увеличения функционала), который передаётся с сервера, без возможности его изменить, вводит через него данные, а всё остальное происходит на сервере, с отправкой результата на телефон"*.

Это меняет объём и характер Android-разработки сильнее, чем что-либо ещё в этой дорожной карте. Отказ от планов Этапов 5–7 версии 1 (native Jetpack Compose экраны Dashboard/Queue/Imagine/Gallery, каждый со своей бизнес-логикой) в пользу следующей модели:

### Что на сервере

- Существующий статический веб-фронтенд Imagine (`comfyui_studio/imagine/static/`) — уже полноценное веб-приложение (HTML/CSS/JS, i18n, темы, WS/поллинг) — **это и есть тот самый "интерфейс", который передаётся телефону**, без переписывания на Kotlin.
- Remote-процесс отдаёт "домашнюю" страницу терминала (`GET /` или `/remote/home`) — список доступных "апп" из **динамического** реестра `apps_registry.py` (решено сразу делать расширяемым, см. §4) — и проксирует статику/API каждого зарегистрированного апп на его собственный путь (`imagine_proxy.py` — реверс-прокси к процессу Imagine, который остаётся отдельным процессом со своим портом, недоступным напрямую снаружи; наружу торчит только порт Remote).
- Расширение функционала в будущем ("доп. приложения/механики") = добавить ещё один пункт в `apps_registry.py` и ещё один proxy-модуль — телефон не нужно обновлять для появления нового пункта меню.

### Что на телефоне (резко упрощённый Android-проект)

Android-приложение больше **не содержит бизнес-логики** ни для одного апп. Оно содержит только:

1. **Discovery** — `NsdManager`, поиск ПК в сети (без изменений от версии 1, см. §4).
2. **Pairing** — единственный полностью нативный экран (до появления токена показывать серверную страницу нечем — сессии ещё нет): ввод 6-значного кода, получение `device_id`/`access_token`, сохранение в `EncryptedSharedPreferences`.
3. **WebView-контейнер ("терминал")** — после pairing показывает `WebView`, направленный на `http(s)://<host>:<port>/`. Всё остальное — Dashboard, очередь, Imagine, будущие апп — это уже отрисовано сервером внутри этого `WebView`, Android его не парсит и не переопределяет.
4. **Минимальный "хром" вокруг WebView**: индикатор соединения, кнопка "сменить ПК" (если сопряжено несколько), pull-to-refresh — не более.

### Технический узел, который нужно решить отдельно: как токен попадает в WebView-сессию

Браузерный `fetch`/`XHR`/`WebSocket` внутри страницы не может сам добавить `Authorization: Bearer <token>` — этот заголовок известен только нативному коду Android. Варианты (зафиксировать один на Этапе 5):

1. **Перехват запросов на уровне `WebViewClient.shouldInterceptRequest`**: Android сам добавляет заголовок `Authorization` к каждому запросу до того, как он уйдёт на сервер. Работает для обычных HTTP-запросов страницы, но **не работает для WebSocket** — WS-запрос в браузерном API не позволяет задавать произвольные заголовки при хендшейке.
2. **Токен прокидывается в саму HTML-страницу при первой (уже аутентифицированной через вариант 1) загрузке** — Remote-сервер при рендере `index.html` вставляет `<script>window.__REMOTE_TOKEN__ = "...";</script>`, и уже сам JS-фронтенд Imagine передаёт этот токен как `?token=...` в URL WebSocket-подключения (эндпоинт `/api/v1/remote/ws` и так уже спроектирован принимать токен через query-параметр, см. §2 — согласуется само собой).
3. Итог: **вариант 1 для обычных запросов + вариант 2 для WS** — комбинация, не требующая переделки веб-фронтенда Imagine, только добавления одной строчки при рендере страницы Remote-сервером.

### Последствия для остальной дорожной карты

- **Этапы 5–7 версии 1 (native Dashboard/Queue/Imagine/Gallery на Kotlin) заменяются на два узких этапа**: (а) WebView-терминал + discovery + pairing на Android, (б) доработка серверной стороны — реестр апп + reverse-proxy + внедрение токена в страницу. Объём Android-кода падает в разы.
- Realtime (WS) логика полностью остаётся в существующем JS веб-фронтенда Imagine — не нужно писать отдельный `RemoteWebSocket.kt`.
- Минус подхода: если в будущем понадобится нативная функциональность телефона (push-уведомления при завершении генерации, когда приложение свёрнуто, доступ к галерее устройства и т.п.) — WebView-модель этого не даёт бесплатно, потребуется отдельный нативный мост (WebView ↔ Kotlin JS-bridge) под конкретную фичу. Это сознательный компромисс, не блокер сейчас.

## Этап 1 — Remote API Core (пакет `comfyui_studio/remote/`, только REST, только LAN) — ✅ Реализовано

Цель: доказать пару «pairing → токен → REST → ответ», без WebView и без Android.

### 1.1 DTO-модели

```python
class RemoteStatus(BaseModel):
    studio_version: str
    comfyui_running: bool
    comfyui_port: int | None
    imagine_running: bool
    gpu_name: str | None
    vram_used_mb: int | None
    vram_total_mb: int | None

class PairingCodeResponse(BaseModel):
    code: str            # "482-731"
    expires_at: datetime
    attempts_left: int

class DeviceToken(BaseModel):
    device_id: str
    access_token: str    # отдаётся ОДИН раз, при pairing

class DeviceInfo(BaseModel):
    device_id: str
    name: str
    created_at: datetime
    last_seen: datetime | None
    revoked: bool

class AppEntry(BaseModel):
    id: str               # "imagine"
    name: str              # "Imagine"
    path: str               # "/apps/imagine/" — префикс проксирования
    icon: str | None = None
```

### 1.2 Эндпоинты

```
GET  /api/v1/remote/status                → RemoteStatus
POST /api/v1/remote/pair/start            → PairingCodeResponse   (локальный вызов из Studio UI)
POST /api/v1/remote/pair/confirm          → DeviceToken           (с телефона: {code, device_name})
GET  /api/v1/remote/devices               → list[DeviceInfo]      (админ-контекст — вызывается из Studio UI)
POST /api/v1/remote/devices/{id}/revoke   → 204
GET  /api/v1/remote/apps                  → list[AppEntry]
GET  /api/v1/remote/queue                 → грубый статус очереди
```

### 1.3 Pairing — протокол (без изменений от версии 1)

```
Studio UI: "Подключить телефон"
   → POST /api/v1/remote/pair/start (без токена, локальный вызов)
   → код: криптографически случайные 6 цифр, TTL 120–300 сек, ≤5 попыток

Android (нативный экран): пользователь вводит код
   → POST /api/v1/remote/pair/confirm {code, device_name}
   → код уничтожается сразу после успеха (одноразовый)
   → генерируются device_id (uuid4) + access_token (256-bit random, base64url)
   → в device_store сохраняется ТОЛЬКО hash(access_token)
   → access_token отдаётся один раз в ответе

Далее:
   Authorization: Bearer <access_token>
   → auth.py находит device по hash(token), проверяет revoked=False, обновляет last_seen
```

### 1.4 Хранилище устройств

`%APPDATA%\ComfyUIStudio\remote_devices.json` — тот же паттерн, что уже используется для `theme.json`/`language.json`. Поля: `device_id`, `name`, `token_hash` (sha256), `created_at`, `last_seen`, `revoked`. Токен в открытом виде на диске никогда не хранится.

### 1.5 Критерий готовности

`curl`/Postman: код в UI Studio → подтверждение → токен → `GET /remote/status` с этим токеном → корректный ответ. Отзыв устройства → 401. Ещё нет ни строчки Android/WebView-кода.

### Как реализовано по факту

Пакет `comfyui_studio/remote/` написан целиком по плану выше (DTO/pairing/device_store/auth/routes), плюс несколько уточнений, которых не было в плане:

- **`local_guard.py`** — эндпоинты, помеченные в §1.2 как «локальный вызов из Studio UI» (`pair/start`, `devices`, `devices/{id}/revoke`), проверяют, что запрос пришёл с `127.0.0.1`/`::1`. В плане это подразумевалось словами «локальный вызов», но не было явного механизма — без него любой человек в той же LAN (а Remote слушает не только на loopback, см. `--host`) мог бы сам выписать себе pairing-код или посмотреть/отозвать чужие устройства.
- **`gpu_stats.py`** — автономный (без Qt) опрос GPU через `pynvml` для полей `gpu_name`/`vram_used_mb`/`vram_total_mb` в `RemoteStatus`. Логика та же, что в `launcher/core/system_monitor.py` (`ResourceMonitor`), но не переиспользуется напрямую — тот класс завязан на `QObject`/таймер, а Remote-процесс сознательно без Qt.
- **`GET /apps`** — реестра приложений (`apps_registry.py`) ещё нет, появится на этапе 4. Эндпоинт уже существует в контракте API и требует токен устройства, но всегда отдаёт пустой список — честный промежуточный ответ вместо предположения «Imagine всегда доступен».
- **Интеграция с лаунчером** (не было в плане этапа 1, но понадобилось для реального тестирования, а не только через голый curl): `launcher/core/remote_process.py` (`RemoteProcess`, по образцу `ImagineProcess`) + диспетчеризация `REMOTE_CLI_FLAG` в корневом `main.py` + раздел «Удалённый доступ» в едином дереве настроек (`ui/settings/remote_page.py`): включение/выключение, получение pairing-кода, список устройств с отзывом. Полностью независим от переключателя «Интерфейс: ComfyUI/Imagine» — можно включить, даже если ComfyUI ни разу не запускался.
- **Порт по умолчанию** — 7861 (не зафиксирован явно в плане), на единицу больше порта Imagine (7860), чтобы оба процесса поднимались одновременно без конфликта портов «из коробки».
- **Зависимости** — отдельной группы `extras` не заводили, Remote использует ту же группу `imagine` в `pyproject.toml` (fastapi/uvicorn/pydantic/python-multipart) — см. комментарий там же.
- **Тесты** — `tests/remote/test_device_store.py` и `test_pairing.py`, чистая логика без Qt (по конвенции `tests/launcher/`).
- **Не проверено вживую**: в песочнице, где писался этот код, не было доступа к сети, чтобы поставить fastapi/uvicorn/pynvml и реально поднять сервер — критерий готовности §1.5 (полный цикл через curl/Postman) предстоит прогнать на реальной машине. Логика pairing/device_store проверена отдельно, напрямую (без fastapi), интерпретатором Python из песочницы.
- **Проверено вживую (2026-09-05)**: полный цикл `pair/start` → `pair/confirm` → `GET /status` с реальным токеном подтверждён на реальной машине пользователя (Windows, `Invoke-RestMethod`) — корректный ответ со всеми полями, включая живые `gpu_name`/`vram_used_mb`/`vram_total_mb` (RTX 5050 Laptop GPU). Единственная накладка была не в самом Remote, а в PowerShell: `curl.exe` в PowerShell ломает JSON-тело в `-d "{\"...\"}"` (не понимает `\"`-экранирование так, как ожидает curl) — README обновлён с рабочими вариантами (`Invoke-RestMethod` или `curl.exe` с одинарными кавычками).

## Этап 2 — Realtime (грубый статус) + WS-инфраструктура для проксирования — ✅ Реализовано

```
GET /api/v1/remote/ws?token=...     (WebSocket)
```

События:

```json
{"type": "queue.update", "running": 1, "pending": 3}
{"type": "generation.started", "prompt_id": "..."}
{"type": "generation.completed", "prompt_id": "...", "image_urls": ["..."]}
{"type": "generation.error", "prompt_id": "...", "message": "..."}
```

Источник данных на MVP — поллинг `/api/generate/{id}/status` бэкенда Imagine изнутри Remote-процесса (`asyncio`-таск раз в 1–2 сек), транслируемый подключённым WS-клиентам. Именно это соединение и есть то самое, куда JS-фронтенд Imagine (уже отрисованный внутри Android WebView) подключится напрямую, используя токен, вставленный в страницу (см. §0.3).

### Как реализовано по факту

Реализовано по плану, с одним практическим уточнением по источнику
списка `prompt_id` (см. подробное объяснение прямо в докстринге
`generation_watcher.py`): на этом этапе подать генерацию через сам
Remote ещё нельзя (реестр апп/reverse-proxy — только этап 4), поэтому
взять НАЧАЛЬНЫЙ список активных `prompt_id` неоткуда, кроме как у
самого ComfyUI — `GenerationWatcher` опрашивает `/queue` ComfyUI (тем
же `ComfyAPIClient`, что и этап 1) раз в 1.5 сек, из него же берёт и
`queue.update`, и множество `running_ids`. Диффом множества между двумя
опросами определяются `generation.started` (id появился) и сам факт
завершения (id пропал); а вот РЕЗУЛЬТАТ завершившегося задания
(готово/ошибка/`image_urls`) — это уже ровно то, что предполагает
дорожная карта: одиночный запрос `GET /api/generate/{id}/status`
бэкенда Imagine, только теперь по конкретному, уже известному
`prompt_id`. Если Imagine не запущен или не знает про такой `prompt_id`
(задание поставлено не через него) — `generation.completed` уходит
честно, с пустым `image_urls`, вместо выдумывания результата.

Дополнительно:
- **`ws_hub.py`** (`ConnectionHub`) — реестр активных WS-подключений,
  один экземпляр на процесс Remote, тот же паттерн синглтона, что и
  `pairing_manager`.
- Токен передаётся query-параметром (`?token=...`), а не заголовком
  `Authorization` — так и предполагалось в §0.3 ("токен, вставленный в
  страницу"), но здесь явно зафиксировано: WS API браузеров/WebView не
  позволяет проставлять произвольные заголовки на этапе handshake.
- `image_urls` в `generation.completed` — абсолютные URL на порт
  Imagine (`http://127.0.0.1:<imagine_port>/api/image?...`), не
  относительные. Это временное решение до этапа 4 (reverse-proxy) —
  тогда правильный путь будет идти через сам Remote
  (`/apps/imagine/...`), а не напрямую на порт Imagine, который снаружи
  локальной сети обычно недоступен; см. комментарий в
  `generation_watcher.py`.
- `queue.update` рассылается только при ИЗМЕНЕНИИ `running`/`pending`
  (не на каждом тике) — не было явно оговорено в плане, но иначе
  каждые 1.5 сек летел бы одинаковый повторяющийся эвент даже при
  полностью пустой и неизменной очереди.
- **Тесты** — `tests/remote/test_generation_watcher.py`, логика диффа
  множеств и оба исхода (успех/ошибка) через Imagine — без реального
  FastAPI/сети (тестовые функции синхронные, оборачивают `await` в
  `asyncio.run()` — в проекте нет `pytest-asyncio`/`anyio`, заводить
  новую тестовую зависимость ради пяти тестов одного модуля не стали).
- **Проверено вживую (2026-09-05)**: полный WS-цикл подтверждён на реальной машине пользователя (Windows, скрипт на `websockets` из README) — `queue.update`/`generation.started`/`generation.completed` с реальными `image_urls` пришли корректно, включая сценарий с НЕСКОЛЬКИМИ параллельно выполняющимися генерациями (три задания внахлёст) — каждое закрылось своим `generation.completed` с правильным набором картинок, без перепутывания между `prompt_id`.

## Этап 3 — Пошаговый прогресс (опционально, не блокирует MVP) — ✅ Реализовано

Без изменений от версии 1: WS-клиент внутри `comfy_client.py` Imagine к `/ws?clientId=<comfy_client.client_id>` ComfyUI → трансляция `progress`/`executing` в `generation.progress` через WS Remote-процесса. Актуально только для заданий, поставленных через Imagine (что и есть единственный сценарий с телефона).

### Как реализовано по факту

Реализовано по плану, с одной находкой, потребовавшей отдельного
исправления ДО того, как сам этап вообще стал возможен: `client_id` у
`ComfyClient` генерировался заново при КАЖДОМ создании экземпляра
(`get_client()` в `main.py` создаёт новый экземпляр на каждый HTTP-
запрос) — при таком поведении ни одно персистентное WS-соединение
никогда не совпало бы по `client_id` с тем, каким реально был
поставлен в очередь конкретный `prompt_id` (ComfyUI шлёт
`progress`/`executing` ТОЛЬКО тому сокету, чей `clientId` совпадает с
`client_id` запроса `POST /prompt`, см. подробный разбор в
`comfyui_studio/launcher/core/comfy_ws.py` — та же особенность, из-за
которой WS-клиент лаунчера не видит эти события для заданий браузера).
Исправлено: `client_id` теперь process-wide константа
(`ComfyClient.PROCESS_CLIENT_ID`), одна на весь процесс Imagine, а не
на экземпляр.

Дальше — по плану, с двумя практическими уточнениями:
- **Только `progress`, не `executing`** — `generation.progress` собирается
  только из сообщений `progress` (несёт `prompt_id`/`value`/`max`).
  `executing`/`executed`/`execution_error` тоже приходят на тот же
  сокет, но `generation.completed`/`generation.error` уже полностью
  покрыты этапом 2 (см. `generation_watcher.py`) — дублировать их ещё и
  отсюда означало бы два независимых источника истины для одного и
  того же события.
- **IPC между процессами** — Imagine и Remote остаются двумя отдельными
  процессами (см. §0.1), поэтому нужен канал доставки: фоновая задача
  `progress_forwarder.py` внутри Imagine пересылает каждое
  `generation.progress` обычным fire-and-forget HTTP POST на новый
  внутренний эндпоинт Remote — `POST /api/v1/remote/internal/
  generation-progress` (`routes/internal.py`, защищён той же проверкой
  "только с 127.0.0.1", что и `pair/start`/`devices*`, см.
  `local_guard.py`, только вызывающая сторона теперь не Studio UI, а
  другой Studio-процесс). Best-effort: если Remote не включён/не
  запущен, пересылка просто не долетает, сам Imagine это не замечает и
  не логирует на каждое отдельное событие (их могут быть десятки в
  секунду).
- Порт Remote передаётся Imagine через новый CLI-аргумент
  `--remote-port` (`imagine/__main__.py` → `IMAGINE_REMOTE_PORT` →
  `progress_forwarder.remote_port`), прокидывается из
  `launcher_window.py` при старте Imagine (настроенный порт, независимо
  от того, включён ли Remote прямо сейчас — сохраняет независимость
  Imagine от Remote, см. §0.1).
- **Новая рантайм-зависимость** — `websockets` (асинхронный WS-клиент
  внутри `progress_forwarder.py`) стала настоящей рантайм-зависимостью
  `imagine`-extras (`pyproject.toml`), а не только тестовой (была уже в
  группе `dev` ради `tests/launcher/test_comfy_ws.py`) — добавлена в
  `collect_all` обоих `.spec`-файлов и в `IMAGINE_REQUIRED_MODULES`
  (`launcher/core/imagine_process.py`).
- **Тесты** — `tests/imagine/test_progress_forwarder.py`: разбор
  WS-сообщений (`_handle_text_message`) и пересылка (`_forward_to_remote`)
  — без реального WS-соединения/сети (то же ограничение, что и у
  `GenerationWatcher._tick()` в этапе 2 — сетевой ввод-вывод самого
  соединения тестируется только вживую).
- **Проверено вживую (2026-09-05)**: полный сквозной цикл подтверждён на реальной машине пользователя — `generation.progress` идёт пошагово (1/8 → 8/8 и т.п.) с корректной привязкой к своему `prompt_id`, включая сценарий, где следующее задание (`generation.started`) уже стартовало и шлёт свой прогресс, пока предыдущее ещё не получило `generation.completed` — никакого смешения прогресса между параллельными `prompt_id` не произошло.

## Этап 4 — Реестр апп + reverse-proxy на сервере — ✅ Реализовано

**Новый этап, появившийся из-за решения §0.3 — заменяет часть содержания старых этапов 5–7.**

- **[Решено — сразу расширяемым]** `apps_registry.py` — не статический список, а реестр с регистрацией во время запуска, концептуально по тому же паттерну, что `tool_registry.register_in_process_app()` для desktop-окон (это два разных реестра, не путать: тот — для Qt-окон монолитного режима, этот — для веб-апп терминала):

  ```python
  # comfyui_studio/remote/apps_registry.py
  @dataclass
  class RemoteApp:
      id: str
      name: str
      path: str                 # префикс проксирования, "/apps/imagine/"
      icon: str | None = None
      proxy_target: Callable[[], str | None]  # -> "http://127.0.0.1:<port>" или None, если апп сейчас не запущен

  def register_app(app: RemoteApp) -> None: ...
  def list_available_apps() -> list[RemoteApp]:
      """Возвращает только те апп, чей proxy_target() сейчас не None —
      сервер сам решает, что реально доступно прямо сейчас, а не просто
      выдаёт статический список."""
  ```
  - Регистрация Imagine происходит там же, где сейчас в `launcher_window.py` управляется его процесс (`ImagineProcess`) — по аналогии с тем, как `register_in_process_app()` уже вызывается для desktop-окон.
  - `GET /api/v1/remote/apps` возвращает результат `list_available_apps()` — если Imagine выключен в данный момент, его плитка на терминале просто не показывается (а не показывается серым/неактивной — сервер сам решает актуальность, телефону не нужно знать причину).
  - Добавление нового апп в будущем = вызов `register_app()` в одном месте кода + свой proxy-модуль — ни Android, ни существующие апп не трогаются.
- `imagine_proxy.py`: `httpx`-based реверс-прокси `/apps/imagine/* → http://127.0.0.1:<imagine_port>/*`, включая проксирование `Range`-запросов для изображений и (при необходимости) WS, если в будущем Imagine обзаведётся собственным WS.
- Домашняя страница терминала (`GET /` или `/remote/home`, отдаётся Remote-процессом): простая серверная HTML-страница со списком апп из реестра — по сути, "рабочий стол" телефона-терминала.
- Именно на этом этапе решается техническая деталь из §0.3 (внедрение токена в HTML при отдаче страницы).

### Критерий готовности

Открыть `http://<pc-ip>:<remote-port>/` в обычном мобильном браузере (ещё без Android-приложения!) с токеном, полученным через curl на Этапе 1, руками подставленным в URL/куки — увидеть список апп, открыть Imagine, сгенерировать картинку, увидеть результат. Если это работает в мобильном браузере, WebView-обёртка на Android — тонкий слой поверх уже рабочего сценария.

### Как реализовано по факту

Реализовано по плану — `apps_registry.py` (`RemoteApp`/`register_app`/
`list_available_apps`, ровно как в примере кода выше), `imagine_proxy.py`
(httpx-based reverse-proxy), домашняя страница (`routes/home.py`) — с
несколькими уточнениями, которых план не расписывал в деталях:

- **Регистрация Imagine — при старте самого Remote (`app.py`, lifespan),
  а не из `launcher_window.py`.** План говорил "регистрация происходит
  там же, где сейчас в `launcher_window.py` управляется его процесс" —
  но это в буквальном смысле невозможно без межпроцессного вызова:
  `launcher_window.py` (Qt-процесс лаунчера) и Remote — РАЗНЫЕ процессы
  (см. §0.1), и `apps_registry` — модуль-уровневый реестр внутри
  процесса Remote, недоступный извне напрямую. Вместо этого Remote
  регистрирует Imagine СНАЧАЛА, при собственном старте (зная порт
  Imagine из `--imagine-port`, переданного тем же `launcher_window.py`
  — тот же параметр, что уже был нужен для `is_imagine_available()` в
  `/status`, см. этап 1), а РЕАЛЬНУЮ доступность прямо сейчас
  по-прежнему решает `proxy_target()` при каждом запросе — тот же дух
  "сервер сам решает, что доступно", просто источник регистрации другой.
- **Токен для "терминальных" маршрутов — заголовок ИЛИ кука ИЛИ
  query-параметр** (`proxy_auth.py`, новый модуль, не было явно в
  плане) — план описывает Android-механику (перехват заголовков,
  §0.3), но чтобы критерий готовности реально прошёл в ОБЫЧНОМ
  мобильном браузере без Android, браузеру нужно как-то доносить токен
  и до статики страницы (JS/CSS/картинки), которую он подгружает сам,
  без единого кастомного заголовка/параметра. Заголовок — для будущего
  Android; кука — то, что реально позволяет браузеру дальше сам
  подгружать всё остальное; query-параметр — только чтобы завести эту
  куку первый раз (сама формулировка критерия готовности — "руками
  подставленным в URL/куки" — уже допускает оба способа).
- **`generation.progress`/HTML-инъекция токена привязаны к КОНКРЕТНОМУ
  запросу, а не к устройству вообще** — `imagine_proxy.py` внедряет в
  HTML именно тот токен, которым была пройдена аутентификация ЭТОГО
  запроса (из заголовка/куки/параметра), а не какой-то отдельно
  хранимый "токен по умолчанию".
- **Тесты** — `tests/remote/test_apps_registry.py` (реестр — чистая
  логика, без FastAPI) и `tests/remote/test_proxy_auth.py` (приоритет
  источников токена, с фейковыми Request/Response вместо настоящего
  FastAPI/TestClient). `imagine_proxy.py` и `routes/home.py` сами по
  себе (HTTP-уровень) юнит-тестами не покрыты — они тонкие обёртки
  вокруг уже протестированной логики (`apps_registry`/`proxy_auth`), а
  полноценная проверка самого проксирования (реальный HTTP до реального
  Imagine, стриминг, `Range`-запросы) имеет смысл только на реальной
  машине, не через моки.
- **Новая рантайм-зависимость** — `httpx` (`imagine_proxy.py`) в
  `imagine`-extras (`pyproject.toml`), добавлена в `collect_all` обоих
  `.spec`-файлов (вместе с `httpcore`) и в `REMOTE_REQUIRED_MODULES`
  (`launcher/core/remote_process.py`).
- **Найден и исправлен при живом тестировании (2026-09-05): статика
  Imagine ломалась через прокси.** Первая версия открылась (страница
  «терминала», плитка Imagine), но сам Imagine внутри не работал:
  консоль браузера показывала 404 на `/css/style.css`, `/js/app.js` и
  т.п., генерация не запускалась вовсе. Причина — HTML/JS/бэкенд
  Imagine писали пути к своим же ресурсам АБСОЛЮТНЫМИ, с ведущим `/`
  (`href="/css/style.css"`, `fetch('/api/generate')`, серверный
  `"url": f"/api/image?..."` и т.п.) — это работает, только пока
  Imagine отдаётся строго с корня своего ORIGIN (`http://host:imagine_port/`).
  Через reverse-proxy страница физически открывается по ДРУГОМУ пути
  (`http://host:remote_port/apps/imagine/`), и браузер резолвит
  абсолютный `/css/style.css` от КОРНЯ ORIGIN Remote

  и на собственном адресе Imagine, и через `/apps/imagine/` (страница —
  одна-единственная, без клиентского роутинга, так что "текущий URL"
  не меняется в течение сессии — см. подробные комментарии в самих
  файлах). Заодно поправлен `generation_watcher.py` (этап 2/3) —
  `image_urls` в `generation.completed` теперь строится как корневой
  ОТНОСИТЕЛЬНЫЙ путь через сам Remote (`/apps/imagine/api/image?...`)
  вместо прежнего `http://127.0.0.1:<imagine_port>/api/image?...` —
  последнее было временным решением, помеченным как таковое ещё на
  этапе 3, и вдобавок содержало отдельный скрытый баг (жёстко прошитый
  `127.0.0.1` на реальном LAN означал бы loopback ТЕЛЕФОНА, а не ПК со
  Studio). Новый тест
  `test_fetch_imagine_status_builds_proxied_relative_urls` в
  `tests/remote/test_generation_watcher.py` проверяет именно сборку
  этого URL (раньше метод в тестах только подменялся целиком, сама
  склейка строк не проверялась — то же самое разошлось бы незамеченным
  и здесь).
  Известное ограничение: стили/пресеты, у которых картинка была
  загружена (`/api/upload-image`) ДО этого исправления, могли сохранить
  в конфиге старый абсолютный путь (`/media/...`) — такие превью не
  подхватят реальный fix задним числом, понадобится переупостроить
  скрин (перезалить картинку) вручную; для новых загрузок всё уже
  относительное.

     запускалось вовсе.

     `AppSettingsDialog._auto_save()`) -- следующий перезапуск Remote
     (и даже перезапуск всей Studio без этого фикса) использовал бы
     старое значение `host`.

  `status_label`, а не блокировкой полей), и `_start_remote()` вместо
  `self.cfg` перечитывает конфиг заново с диска (`load_config()`) при
  каждом запуске Remote.

## Этап 5 — mDNS discovery — ✅ Реализовано (серверная часть)

Без изменений от версии 1: `zeroconf` (Python) на сервере, `NsdManager` на Android. Отдельный прогон сборки через оба `.spec`-профиля.

### Как реализовано по факту

Серверная часть реализована по плану — `comfyui_studio/remote/mdns.py`
(`MdnsAdvertiser`), новая зависимость `zeroconf` (в `imagine`-extras,
`collect_all` обоих `.spec`, `REMOTE_REQUIRED_MODULES`). `NsdManager` на
Android — вне рамок этого этапа, появится вместе с этапом 6.

Уточнения, не расписанные в плане детально:

- **Тип сервиса** зафиксирован как константа `SERVICE_TYPE =
  "_comfyuistudio._tcp.local."` (см. `mdns.py`) -- собственный, а не
  общий `_http._tcp`, чтобы телефон отличал именно ComfyUI Studio от
  случайных других HTTP-серверов в той же Wi-Fi. Android-реализации
  (этап 6+) нужно использовать РОВНО эту же строку в `NsdManager`.
- **Объявляется, только если включён доступ по локальной сети**
  (`host == "0.0.0.0"`, тот же чекбокс из этапа 4/8) — рекламировать
  сервис, слушающий исключительно `127.0.0.1`, бессмысленно: до него
  всё равно не достучаться ни по какому адресу, полученному через mDNS.
- **Async-вариант `zeroconf`** (`zeroconf.asyncio.AsyncZeroconf`), не
  синхронный `Zeroconf()` — Remote целиком asyncio/FastAPI, регистрация/
  снятие происходят прямо в существующем `lifespan` (`app.py`), тем же
  паттерном, что и запуск/остановка `GenerationWatcher` рядом.
- **LAN-адрес для объявления** переиспользует `get_lan_ip()` из
  `launcher/core/remote_process.py` (тот же хелпер, что уже показывает
  подсказку-адрес в `ui/settings/remote_page.py`, см. этап 4) — не
  дублирует логику определения LAN IP.
- **Не критично для работы Remote** — любая ошибка при регистрации
  (сеть недоступна, порт занят и т.п.) логируется и проглатывается, а
  не роняет процесс — Remote продолжает работать по прямому IP, как и
  без mDNS.
- **Тесты** — `tests/remote/test_mdns.py`: все переходы (host не LAN,
  LAN IP не определился, успешная регистрация, `stop()` без
  предшествующего `start()`, ошибка при регистрации) — с фейковым
  `AsyncZeroconf`, без реальной сети. Прогнано и вручную интерпретатором
  в песочнице (с заглушками вместо пакета `zeroconf`, которого там нет)
  — все 6 сценариев отработали как ожидалось.
- **Не проверено вживую**: то же ограничение песочницы, что и на
  предыдущих этапах — сама рассылка mDNS и её реальное обнаружение
  (например, тем же `zeroconf` в роли browser'а с другого устройства в
  сети) ещё предстоит проверить на реальной машине.

## Этап 6.4 — Запуск приложений через Remote — ✅ Реализовано

**Проблема, которую решает:** до этого этапа `apps_registry.py` только
наблюдал за Imagine (см. §Этап 4) — плитка на терминале появлялась
ТОЛЬКО если Imagine уже был запущен вручную через Studio UI на ПК.
С телефона нельзя было даже увидеть приложение, не то что открыть его,
пока не подойдёшь к компьютеру — при том что сам запуск (subprocess)
никак не завязан на Qt/окно лаунчера.

**Что сделано:**
- `apps_registry.RemoteApp` получил два новых поля: `status_fn()`
  (`"running"` / `"starting"` / `"stopped"` — третье промежуточное
  состояние специально добавлено, чтобы телефон видел "запускается…",
  а не просто зависшую кнопку, пока Imagine поднимается — это может
  занимать заметное время, как и было отмечено в фидбэке по этапу 6)
  и `start_fn()` (опционально — не все будущие приложения обязаны
  уметь стартовать с телефона).
- Новый `app_launcher.py` — НЕ дублирует логику запуска: целиком
  переиспользует уже существующий `launcher.core.imagine_process.
  ImagineProcess`/`resolve_imagine_launch` (тот же код, которым Studio
  UI и так пользуется для своей кнопки "Запустить"). Это безопасно
  ровно потому, что тот модуль не импортирует Qt ни при каких
  обстоятельствах (подтверждено: процесс Remote в принципе не
  импортирует Qt, см. `REMOTE_CLI_FLAG` в `main.py`) — запуск просто
  инициируется из процесса Remote вместо Qt-кнопки. Лок на повторный
  запуск, пока предыдущий ещё не поднялся (защита от гонки, если
  пользователь несколько раз подряд нажмёт "Запустить" на телефоне).
- `GET /apps` теперь отдаёт ВСЕ зарегистрированные приложения (не
  только запущенные) с полями `status`/`startable`.
- `POST /apps/{id}/start` (Bearer, как обычный REST-эндпоинт для
  устройства, не `require_loopback`) — запускает приложение, отвечает
  202 с текущим статусом (почти всегда `"starting"`, не `"running"` —
  запуск асинхронный).
- Домашняя страница терминала (`routes/home.py`) — плитка вместо
  ссылки превращается в кнопку "Запустить" для незапущенных
  запускаемых приложений; клик дёргает `POST /start` с
  `Authorization: Bearer` из `window.__REMOTE_TOKEN__` (обычный
  `fetch()` умеет заголовки — в отличие от WS-хендшейка, ограничение
  из §0.3 здесь не действует), затем опрашивает `GET /apps` раз в 2с
  до статуса `"running"` и перезагружает страницу.

**Как проверено:** живой прогон через `fastapi.testclient.TestClient`
в этой рабочей среде (не на Windows, без реального ComfyUI) —
pairing → `GET /apps` (status="stopped", startable=true) →
`POST /apps/imagine/start` → реальный subprocess (`python -m
comfyui_studio.imagine ...`) фактически поднялся и стал отвечать на
`GET /` за ~1.5 секунды → статус корректно стал `"running"` →
повторный вызов `/start`, пока процесс уже жив, не породил второй
процесс (вернул `"running"` без побочных действий) → `stop()`
корректно завершил процесс. Разумеется, это не заменяет проверку на
вашей машине с настоящим ComfyUI/Imagine и реальным Android-клиентом —
но сама механика запуска, отслеживания статуса и REST-контракта
подтверждена сквозным тестом, а не только синтаксической проверкой (в
отличие от этапа 6, где такой прогон был невозможен из-за отсутствия

**Не сделано:** аналогичного `start_fn` для других будущих приложений

## Этап 6.5 — Push-уведомления — ✅ Реализовано, требует Firebase-проекта пользователя для живого теста

**[Решено — используем FCM]** Проверил актуальную стоимость: Firebase Cloud Messaging как сервис доставки push бесплатен без ограничений по количеству сообщений на обоих тарифах Firebase (Spark и Blaze) — платными могут быть только другие сервисы Firebase (Firestore, SMS-аутентификация и т.п.), которые в этом проекте не нужны. Для одного (или нескольких) личных устройств это ничего не будет стоить, поэтому self-hosted UnifiedPush/ntfy как основной вариант не нужен — оставляем его только на заметку, если в будущем принципиально захочется отказаться от Google-инфраструктуры.

Это единственная функция, которая по своей природе не укладывается в модель "чистого терминала" (§0.3): пока приложение свёрнуто или экран выключен, WebView и его JS не выполняются, поэтому WS-событие `generation.completed` из §2 никто не увидит. Технически это требует нативного канала доставки, не завязанного на то, что WebView вообще открыт.

### Реализация

1. Завести Firebase-проект (бесплатно), получить service account JSON для сервера и `google-services.json` для Android-проекта.
2. **На сервере**: при регистрации устройства (`POST /pair/confirm`) Android дополнительно передаёт свой FCM-токен; он хранится в `device_store.json` рядом с `token_hash`. При событии `generation.completed`/`generation.error` Remote-процесс, помимо WS-рассылки (§2), делает вызов FCM HTTP v1 API с этим токеном.
3. **На Android**: интеграция `firebase-messaging`, получение токена при первом запуске, обновление на сервере при его смене (FCM токены иногда переиздаются), обработка входящего push в `FirebaseMessagingService` — по тапу открывает `TerminalActivity` сразу на нужном апп.
4. **Требование к сети**: серверу (ПК) нужен исходящий доступ в интернет к API Google для отправки push — это не проблема, поскольку доступ вне дома (§9) и так предполагает, что ПК смотрит в интернет.

### Критерий готовности

Свернуть/закрыть приложение на телефоне → запустить генерацию с ПК напрямую (в обход телефона) → получить push по завершении → тап открывает терминал на результате.

> **Как реализовано по факту (2026-09-07):**
>
> **Сервер** (`comfyui_studio/remote/`):
> - `device_store.py` — `Device.fcm_token` (опционально), `create_device(name, fcm_token=None)`, новые `update_fcm_token()`/`list_fcm_tokens()` (последняя уже исключает отозванные устройства — та же логика, что у обычной Bearer-аутентификации в `auth.py`, чтобы не пришлось помнить это правило в каждом вызывающем месте).

Путь к сервис-аккаунту — `cfg["remote"]["fcm_service_account_path"]` в `config.json` (та же Qt-независимая `launcher.core.config.load_config()`, что и в `comfy_launcher.py`/`app_launcher.py` — см. их докстринги), не переменная окружения и не хардкод. Если путь не настроен — тихо ничего не отправляется, это не должно ронять Remote или как-либо блокировать основную WS-доставку.
> - **Важное уточнение по факту, не по плану**: сообщения FCM отправляются **только с `data`, без `notification`** — при обоих блоках сразу Android показывает уведомление СИСТЕМОЙ напрямую, в обход `FirebaseMessagingService.onMessageReceived`, когда приложение свёрнуто/убито — то есть ровно в том случае, ради которого push вообще нужен. Системное уведомление в этом случае вело бы по тапу в приложение по умолчанию, без перехода сразу на нужный апп. Только `data`-payload гарантирует, что `onMessageReceived` вызывается ВСЕГДА, независимо от состояния приложения.
> - `generation_watcher.py` — `_notify_push()` вызывается рядом с `_hub.broadcast()` на обоих событиях, через `asyncio.create_task(asyncio.to_thread(...))` (не блокирует тик опроса очереди реальным сетевым вызовом к Google).
> - `pyproject.toml` — добавлена зависимость `google-auth`.
> - **Qt-настройки** (`ui/settings/remote_page.py`) — новая группа "Push-уведомления": путь к JSON сервис-аккаунта (`QFileDialog` + кнопка "Очистить"), сохраняется в `cfg["remote"]["fcm_service_account_path"]` (добавлено в `DEFAULT_CONFIG` в `constants.py`). Заводить сам Firebase-проект — по-прежнему вручную в консоли Google, это единственное, что эта страница в принципе не может сделать за пользователя.
>
> **Android** (`android/`):
> - `app/build.gradle.kts` — `firebase-bom`/`firebase-messaging-ktx`; плагин `com.google.gms.google-services` применяется **условно**, только если `google-services.json` реально лежит в `android/app/` (проверка `file(...).exists()` в самом build-скрипте) — без этого сборка ломалась бы для всех, кто ещё не завёл свой Firebase-проект, хотя push — опциональная функция и не должна быть условием сборки вообще.
> - **Новый `fcm/FcmService.kt`** — `onNewToken()` шлёт обновлённый токен на сервер через `RemotePairingClient.updateFcmToken()` (новый метод в уже существующем классе, не отдельный файл — та же логика, что у `RemotePairingClient` на этапе 6: один дополнительный REST-вызов не оправдывает `RemoteApi.kt`, которого роадмап явно требует избежать); `onMessageReceived()` строит уведомление вручную (Firebase не показывает его сам — см. "важное уточнение" выше про `data`-only), тап открывает `TerminalActivity` с `EXTRA_OPEN_PATH = "/apps/imagine/"` — терминал загружает сразу этот путь вместо домашней страницы со списком плиток.
> - `PairingScreen.kt` — `fetchFcmTokenOrNull()` запрашивает токен прямо перед `pair/confirm` (не заранее, чтобы не разносить логику на два места), оборачивает callback-API Firebase (`Task<String>`) в suspend-функцию; ловит `IllegalStateException` (Firebase не инициализирован, если `google-services.json` не был положен) — в обоих случаях (нет Firebase / не удалось получить токен) pairing продолжается без push, а не падает.

> - `AndroidManifest.xml` — декларация `FcmService` (`exported=false`, intent-filter `MESSAGING_EVENT`), разрешение `POST_NOTIFICATIONS`.
> - Новый `res/drawable/ic_notification.xml` — простая белая vector-иконка для статус-бара (Android рисует её как силуэт/маску, не полноцветно).

> **Как проверено:** сквозной тест без единого мока бизнес-логики — pairing с `fcm_token` в теле → токен реально сохранился в `device_store.json` → `POST /fcm-token` реально обновил его на новый → `POST /fcm-token` без `Authorization` реально отклонён 401 → `send_generation_push()` реально дошла до попытки OAuth2-запроса к `oauth2.googleapis.com` (сеть этой рабочей среды не пропускает такие домены, что и было целью проверки: ошибка поймана и залогирована, а не вылетела наружу необработанным исключением) — с реальным (самоподписанным) сервис-аккаунтом `google-auth` корректно распарсил JSON и извлёк `project_id`. > **Не проверено (не может быть проверено в этой рабочей среде):** сама доставка push через реальный Firebase-проект и получение его на реальном Android-устройстве — для этого нужен настоящий Firebase-проект пользователя (`google-services.json` + service account JSON), сеть этой песочницы не пропускает домены Google API. Отдаю на тест вам, как и с этапом 6.
>
> **Живой баг (2026-09-08):** после настройки Firebase (`google-services.json` + сервис-аккаунт в Studio) push всё равно не пришёл. Причина — устройство было сопряжено ещё ДО того, как Firebase появился в проекте, а FCM-токен запрашивается и отправляется на сервер только один раз, во время `pair/confirm` (`PairingScreen.kt`). Уже сопряжённое устройство при каждом следующем запуске уходит из `MainActivity` сразу в `TerminalActivity`, минуя `PairingScreen` целиком — токен так и не попадает на сервер, а `onNewToken()` в `FcmService.kt` сработает только когда Firebase сам захочет его переиздать (не гарантировано и не скоро).
>
> **Фикс:** получение токена вынесено из `PairingScreen.kt` в общий `fcm/FcmTokenUtils.kt` (`fetchFcmTokenOrNull()` + новая `syncFcmTokenIfPaired()`), и `TerminalActivity.kt` теперь досылает текущий токен на сервер при **каждом** открытии терминала (фоновая корутина, `LaunchedEffect(device)`), а не только во время pairing. Идемпотентно и дёшево — если токен уже актуален, повторная отправка `POST /fcm-token` просто перезаписывает тем же значением. Это единственный надёжный способ довезти токен до сервера для уже сопряжённых устройств, у которых Firebase появился позже самого pairing.
>
> Заодно — по тому же живому отчёту, "загрузка Imagine длилась дольше пары минут при первом запуске" (холодный старт ComfyUI, модели ещё не в кэше ОС) — это ожидаемое поведение (см. этап 6, "заметные лаги и долгая первая загрузка... не блокер"), но опасно близко к прежнему таймауту ожидания ComfyUI в цепочке автозапуска (§Этап 6.4). `_COMFY_STARTUP_TIMEOUT_S` увеличен со 180 до 300 секунд, чтобы холодный старт на медленном диске не обрывался ложным таймаутом прямо перед тем, как ComfyUI всё-таки поднимется.
>
> **Живой краш сразу после этого фикса (2026-09-08):** приложение падало на старте с `NetworkOnMainThreadException` в `RemotePairingClient.updateFcmToken`, вызванной из `syncFcmTokenIfPaired`. Причина — `TerminalActivity.kt` вызывает `syncFcmTokenIfPaired()` из `LaunchedEffect`, который выполняется на главном потоке (`AndroidUiDispatcher`), а `updateFcmToken()` делает синхронный OkHttp-запрос; `PairingScreen.kt` у себя оборачивал такой же вызов в `withContext(Dispatchers.IO)`, но `syncFcmTokenIfPaired()` — нет. **Фикс:** переключение на `Dispatchers.IO` перенесено ВНУТРЬ самой `syncFcmTokenIfPaired()` (`fcm/FcmTokenUtils.kt`) — обязанность делать сетевой вызов на правильном потоке теперь у функции, которая его делает, а не у каждого вызывающего кода по отдельности (не полагаемся на то, что будущие вызовы вспомнят обернуть). `FcmService.kt::onNewToken` этот баг не затрагивал — там уже используется настоящий фоновый поток (`kotlin.concurrent.thread`).

## Этап 7 — Действия с очередью: то, что реально доступно

**[Уточнение по ответу №2]**: в текущем коде **нет** отмены конкретного элемента очереди. Есть только:

```
POST /api/generate/{prompt_id}/interrupt → client.interrupt() → POST <comfyui>/interrupt
```

— и этот вызов **глобальный**: он останавливает то, что ComfyUI выполняет прямо сейчас, независимо от переданного в URL `prompt_id` (сам параметр в обработчике не используется и ни на что не влияет). Отмены конкретного *ожидающего* задания в очереди сейчас нет нигде в проекте.

Варианты для дорожной карты:

1. **MVP-скоуп (рекомендация):** в веб-интерфейсе (и, соответственно, на терминале) доступна только кнопка "Остановить текущую генерацию" (`interrupt`), без удаления отдельных элементов очереди. Ничего нового писать не нужно — эндпоинт уже есть, поведение просто честно отражается в UI как "остановить то, что выполняется сейчас", а не "отменить это конкретное задание".
2. **Если понадобится отмена именно ожидающих заданий:** ComfyUI поддерживает это нативно через `POST /queue {"delete": ["<prompt_id>"]}` на своём собственном API — `comfy_client.py` такой метод пока не реализует, это отдельная небольшая доработка (не блокер, но раньше не было учтено ни в одном из планов).

## Этап 9 — Доступ вне домашней сети (личное использование)

**[Корректировка по ответу №3]**: третьей стороны (публичного Relay-сервиса, требующего отдельного хостинга/домена/оплаты) для чисто личного использования не нужно. Рекомендуемый путь — не строить собственный Relay, а использовать готовый механизм "виртуальной локальной сети" (WireGuard или Tailscale/Headscale поверх него): **в обоих случаях Remote API и Android-терминал вообще не знают о существовании VPN** — они просто видят "локальную сеть", и весь код Этапов 1–8 не меняется вообще.

### Уточняющий вопрос пользователя: телефон уже постоянно под своим VPN — можно ли вшить WireGuard в терминал-приложение так, чтобы он поднимал туннель только для себя, не перехватывая весь остальной трафик телефона (и не заставляя выключать основной VPN)?

Коротко: **технически возможно, но с важной оговоркой, которая не зависит от того, встроен WireGuard в приложение или нет** — это ограничение самой платформы Android, а не архитектуры проекта.

**Ограничение платформы.** Android разрешает только **одно активное системное VPN-соединение (`VpnService`) одновременно** на обычном пользовательском профиле. Официальное приложение WireGuard, Tailscale и любое собственное VPN, встроенное в наш терминал через штатный Android VPN API, — все они регистрируются как `VpnService`. Значит, **простое встраивание** WireGuard-клиента в приложение (даже с ограничением на конкретные приложения через `addAllowedApplication()`, что само по себе решает "не весь трафик") всё равно на уровне системы отключит основной VPN пользователя на время, пока активен туннель терминала — просто это будет происходить автоматически при открытии/закрытии приложения, а не вручную через переключение между двумя VPN-приложениями. Для многих сценариев этого достаточно (не нужно руками ничего переключать), но это не "оба VPN работают одновременно".

Два реалистичных варианта — стоит явно выбрать один как решение, а не откладывать:

| Вариант | Как работает | Совместимость с основным VPN | Сложность |
|---|---|---|---|
| **A. Встроенный WireGuard как системный `VpnService`** (`com.wireguard.android:tunnel` — та же библиотека, что использует официальное приложение) | Приложение само поднимает/гасит туннель при открытии/закрытии, `addAllowedApplication(packageName)` ограничивает его только своим трафиком | Основной VPN автоматически приостанавливается, пока открыт терминал, и включается обратно сам, когда терминал закрыт/свёрнут — без ручных действий пользователя | Низкая — готовая, поддерживаемая библиотека, минимум интеграционного кода |
| **B. WireGuard в userspace как приватный "прокси" именно для сетевых вызовов приложения** (например, через `wireguard-go`/`boringtun`, собранные под Android и используемые не как `VpnService`, а просто как шифрующий сокет, через который `OkHttp`/`WebView`-запросы этого приложения ходят к серверу напрямую) | Приложение открывает обычный UDP-сокет к WG-пиру и само шифрует/маршрутизирует только свой трафик — Android вообще не считает это VPN, `VpnService` не задействуется | Полностью независимо от основного VPN — оба работают одновременно, ничего не приостанавливается | Значительно выше — нет готовой Android-библиотеки "из коробки" под такую модель использования, нужна сборка/поддержка нативной WG-реализации (JNI/gomobile) и своя интеграция с сетевым стеком WebView (WebView не даёт напрямую подставить кастомный сокет-провайдер под капотом — потребуется либо локальный HTTP(S)-прокси на `127.0.0.1` внутри приложения, который сам ходит через WG-сокет, и направление WebView через `WebViewClient`/`ProxyController` на этот локальный прокси) |

**Рекомендация:** начать с **варианта A** на Этапе 9 — он покрывает исходную жалобу (не нужно руками переключаться между VPN-приложениями), и его реализация занимает часы, а не недели. Вариант B оставить как возможное будущее улучшение, если на практике окажется, что автоматическая приостановка основного VPN во время сессий с терминалом реально мешает (например, если сессии с генерацией долгие и в это время нужен одновременно и основной VPN для чего-то ещё).

### Решено: начинаем с варианта A, с заделом на переход к варианту B

Чтобы переход к B в будущем не потребовал переписывать весь сетевой слой терминала, стоит с самого начала спрятать способ соединения с сервером за одной точкой абстракции, а не завязывать `AuthWebViewClient`/pairing-логику напрямую на `com.wireguard.android.backend.GoBackend`:

```kotlin
// terminal/tunnel/TunnelProvider.kt
interface TunnelProvider {
    suspend fun connect(config: TunnelConfig): TunnelHandle
    suspend fun disconnect(handle: TunnelHandle)
    fun baseUrl(handle: TunnelHandle): String   // куда WebView/HTTP-клиент должны идти
}

// Этап 9 (вариант A): системный VpnService, addAllowedApplication(packageName)
class VpnServiceTunnelProvider : TunnelProvider { ... }

// Будущий вариант B: userspace WG + локальный HTTP(S)-прокси на 127.0.0.1,
// на который направляется WebView через ProxyController — тот же интерфейс,
// TerminalActivity и pairing-логика не меняются вообще.
class UserspaceTunnelProvider : TunnelProvider { ... }
```

`TerminalActivity` и весь код Этапов 6–8 работают только через интерфейс `TunnelProvider`, не зная, какая реализация активна. Переход на B в будущем — это добавление нового класса и одна строчка выбора реализации, а не переработка терминала.

Публичный Relay (как в версии 1 дорожной карты) по-прежнему откладывается на неопределённый срок и рассматривается только если встанет задача раздавать доступ друзьям без установки VPN-клиента на их стороне.
