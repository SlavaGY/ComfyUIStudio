# Поднимаем OpenSSH-сервер на Windows (вариант B, без VPN)

Второй, независимый от WireGuard способ доступа вне дома — через
обычный SSH с проксированием портов. В отличие от WireGuard-варианта,
здесь **не потребуется** повторять шаги с `netsh ... weakhostreceive`
— причина ниже, в шаге 6.

## 1. Включите OpenSSH Server

PowerShell от имени администратора:

```powershell
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Start-Service sshd
Set-Service -Name sshd -StartupType Automatic
```

## 2. Создайте отдельную урезанную учётную запись

Не используйте свою обычную учётную запись Windows — заведите новую,
специально под это, без прав администратора:

```powershell
$password = Read-Host -AsSecureString
New-LocalUser -Name "comfyui-ssh" -Password $password -PasswordNeverExpires -UserMayNotChangePassword
```

Пароль можно ввести любой сложный — вход всё равно будет только по
ключу (см. шаг 4), пароль этой учётной записи нигде вводиться не будет
(кроме следующего шага — один раз, вручную).

**Обязательно сразу же дайте учётной записи один раз реально войти в
систему**, прежде чем создавать что-либо в её папке профиля:

```powershell
runas /user:comfyui-ssh cmd
```

Введите пароль, заданный выше — откроется отдельное окно cmd, его
можно сразу закрыть, оно было нужно только чтобы Windows создала
настоящий профиль. Это важно: если создать `C:\Users\comfyui-ssh\.ssh`
вручную ДО первого реального входа, Windows при этом самом первом
входе обнаружит, что папка с ожидаемым именем уже занята, и создаст
профиль в другом месте — `C:\Users\comfyui-ssh.<ИМЯ-ПК>` — а всё, что
вы положили в `.ssh` заранее, останется в «пустышке», которую Windows
OpenSSH просто не увидит (сервер при этом будет молча откатываться на
пароль, без явной ошибки — эта проблема далась непросто именно из-за
того, что причина никак не проявлялась напрямую). Проверить, что
профиль настоящий, можно так:

```powershell
Test-Path "C:\Users\comfyui-ssh\NTUSER.DAT"
```

Должно быть `True`. Если `False` — проверьте `Get-ChildItem "C:\Users"
-Directory | Where-Object { $_.Name -like "comfyui-ssh*" }`: если
нашлась папка с суффиксом вроде `comfyui-ssh.DESKTOP-XXXXX` — это и
есть настоящий профиль, используйте именно её путь во всех
последующих шагах гайда вместо простого `C:\Users\comfyui-ssh`.

## 3. Сгенерируйте пару ключей для телефона

В любом PowerShell/cmd на этом же ПК:

```powershell
ssh-keygen -t ed25519 -f phone_key -N '""'
```

Появятся два файла: `phone_key` (приватный — это то, что импортируется
в приложение на телефоне) и `phone_key.pub` (публичный — остаётся на
сервере, см. следующий шаг).

## 4. Разрешите этот ключ для новой учётной записи

Оба варианта, укажите тот, что проще:

**Через PowerShell** (от имени администратора, из папки, где создались
файлы ключей):

```powershell
$sshDir = "C:\Users\comfyui-ssh\.ssh"
$authKeysPath = "$sshDir\authorized_keys"
New-Item -ItemType Directory -Force -Path $sshDir | Out-Null
Copy-Item phone_key.pub $authKeysPath

# ВАЖНО: закрываем наследование и выдаём права ДО смены владельца, а не
# после (проверено на практике -- если сменить владельца раньше, чем
# выданы явные права, можно самого себя запереть из папки, которую сам
# же только что создал: как только владелец меняется на comfyui-ssh, у
# вашей собственной учётки может не остаться никаких прав на этот путь
# вообще, и дальнейшие icacls/Remove-Item начнут получать "Отказано в
# доступе" на ровном месте). "Администраторы" в списке ниже НЕ мешает
# Windows OpenSSH принять ключ -- проверка отклоняет только слишком
# широкий доступ вроде "Все"/"Прошедшие проверку", а не любое
# дополнительное право вообще.
icacls $sshDir /inheritance:r
icacls $sshDir /grant "comfyui-ssh:(OI)(CI)F" /T
icacls $sshDir /grant "SYSTEM:(OI)(CI)F" /T
icacls $sshDir /grant "Администраторы:(OI)(CI)F" /T
icacls $sshDir /setowner "comfyui-ssh" /T
```

Windows OpenSSH очень придирчив к правам доступа на `.ssh`/`authorized_keys`
— если права слишком открытые (например, унаследованы от родительской
папки и разрешают доступ более широкому кругу учётных записей), сервер
тихо откатывается на запрос пароля вместо ключа, без явной ошибки
клиенту. Чтобы увидеть точную причину, если что-то всё же пойдёт не
так — включите подробный лог сервера ДО первой попытки подключения:
в `C:\ProgramData\ssh\sshd_config`, в общей части файла (не внутри
`Match`-блока), добавьте `LogLevel DEBUG3` и перезапустите службу
(`Restart-Service sshd`) — тогда в Event Viewer → «Журналы приложений
и служб» → OpenSSH → Operational появится конкретная причина отказа
человеческим текстом (например, `bad ownership or modes for file`),
а не молчание.

## 5. Ограничьте учётную запись только пробросом портов

Откройте `C:\ProgramData\ssh\sshd_config` (обычный текстовый файл,
Блокнотом от имени администратора) и добавьте в конец:

```
Match User comfyui-ssh
    AllowTcpForwarding yes
    X11Forwarding no
    PermitTTY no
    ForceCommand echo "Эта учётная запись — только для проброса портов"
```

Это значит: ключом можно только открывать `direct-tcpip`-каналы
(именно это и делает приложение), но нельзя получить обычный шелл или
выполнить произвольную команду. Перезапустите службу, чтобы правило
подхватилось:

```powershell
Restart-Service sshd
```

## 6. Порт и проброс

По умолчанию SSH слушает порт 22 — можно оставить как есть или сменить
на другой (например `2222`) через `Port` в том же `sshd_config`, если
хочется отличаться от типичных сканеров портов в интернете. Пробросьте
этот порт на роутере (или используйте тот же IPv6-адрес ПК, что и для
WireGuard, если проброс портов недоступен из-за CGNAT — см.
`WireGuard_Server_Setup.md`, там же объяснение, как это диагностировать).

**Почему здесь не нужен `netsh ... weakhostreceive` (в отличие от
WireGuard):** там проблема была в том, что пакет приходил на ОДИН
адаптер (WireGuard), но был адресован IP-адресу СОВСЕМ ДРУГОГО адаптера
(Wi-Fi) — Windows такое отбрасывала. Здесь ситуация другая: SSH-сервер
сам принимает соединение на порт, на котором слушает (это происходит
нормально независимо от адаптера) — а уже ВНУТРИ себя, от имени
обычного процесса на этой же машине, открывает НОВОЕ, обычное исходящее
соединение к `192.168.1.15:7861` (или порт, на котором у вас слушает
Remote). Исходящее соединение к собственному IP-адресу этой же машины
Windows обрабатывает нормально всегда, без специальных настроек.

## 7. Firewall для входящего SSH-порта

Тот же PowerShell-путь, что и для WireGuard, только TCP вместо UDP —
через `wf.msc` создайте правило для входящего **TCP** на выбранный порт
(22 или ваш кастомный), разрешённое на всех трёх профилях (Домен/
Частный/Публичный).

## 8. Проверка перед импортом в приложение

С Termux на телефоне (на мобильных данных, не на домашнем Wi-Fi):

```bash
pkg install openssh -y
ssh -i phone_key -p 22 -N -D 1080 comfyui-ssh@<адрес ПК>
```

(Файл `phone_key` нужно будет как-то скопировать на телефон для этого
теста — например, через `termux-setup-storage` и обычную папку
Загрузки, или просто вставить содержимое через `nano ~/phone_key` и
`chmod 600 ~/phone_key`. Если адрес — IPv6, указывайте его БЕЗ
квадратных скобок в этой команде — `ssh` их не понимает в отличие от
некоторых других инструментов, квадратные скобки нужны только там, где
явно указан порт через `:` после адреса, как в `[адрес]:порт`.)

**Важно: `-N` обязателен**, иначе получите ложное "не работает" —
без него `ssh` дополнительно пытается открыть обычную сессию (shell),
а `ForceCommand` из шага 5 тут же завершает её после вывода своего
сообщения — из-за чего клиент решает, что делать больше нечего, и
обрывает СРАЗУ ВСЁ соединение целиком, включая проброс портов, ещё до
того, как вы успеете его проверить. `-N` говорит клиенту вообще не
запрашивать сессию — тогда обрывать нечему, и проброс держится, пока
вы сами не прервёте (Ctrl+C).

Если подключение прошло — терминал просто "зависнет" без вывода и без
возврата к приглашению (это и есть ожидаемое поведение с `-N`, а не
зависание/ошибка) — открывайте ДРУГУЮ вкладку Termux:

```bash
curl -v --socks5 localhost:1080 http://192.168.1.15:7861
```

Тот же `401 Unauthorized` с HTML от Remote, что мы уже видели при
проверке WireGuard — значит всё в порядке, весь путь работает.

## 9. Импорт в приложение

Содержимое файла `phone_key` целиком (текст, начинающийся с
`-----BEGIN OPENSSH PRIVATE KEY-----`) — это то, что импортируется в
ComfyUI Studio → кнопка **SSH** → поле приватного ключа. Адрес, порт
(22 или ваш кастомный) и имя пользователя (`comfyui-ssh`) — в
соответствующие поля того же экрана.

Если стандартный файловый менеджер на телефоне не показывает файл
`phone_key` (частая проблема именно с файлами без расширения) —
приложение теперь при импорте ключа открывает системный выбор
приложения (а не сразу то, что назначено обработчиком по умолчанию) —
выберите там Google Files или любой другой менеджер, который такие
файлы видит.
