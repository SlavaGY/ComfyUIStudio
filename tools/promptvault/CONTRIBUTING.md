## Архитектурное правило

**MainWindow ничего не знает о том, как фильтруются/сортируются генерации,
как они хранятся, синхронизируются или редактируются.** Он только:

1. Создаёт виджеты.
2. Подключает их сигналы к методам `GalleryManager`.
3. Подключает сигналы `GalleryManager` к обновлению виджетов.
4. Обрабатывает чисто UI-события (горячие клавиши, позиционирование попапов,
   диалоги подтверждения перед разрушительными действиями типа удаления).

Если вы добавляете новую бизнес-логику (новый фильтр, новое поле генерации,
новую операцию с БД) — она должна жить в `app/core/`, а не в `app/ui/`.
UI-виджеты (`GenerationCard`, `FilterPopup`, `MetadataEditor` и т.д.) не
должны напрямую дёргать `GenerationRepository` или мутировать состояние —
только эмитить сигналы с намерением пользователя (какой id/список id,
какое новое значение), а `GalleryManager` уже решает, что с этим делать.

Массовые операции следуют тому же принципу: `GenerationList` эмитит
`multipleFavoriteChanged(ids, value)` / `multipleRatingChanged(ids, value)` /
`deleteFromLibraryRequested(ids)` и т.д., `MainWindow` в ответ на
разрушительные действия (удаление) показывает `QMessageBox.question` для
подтверждения, а сама операция выполняется в `GalleryManager`.

## Константы

Все "магические числа" (высота карточки, интервалы таймеров, версия
приложения, путь к иконке и т.п.) должны жить в `app/config.py`, а не быть
захардкожены в месте использования.

## Логирование

Используйте `logging.getLogger(__name__)` в начале модуля — не
`print()`. Логи пишутся в `~/.promptvault/logs/` и дублируются в stdout
(см. `app/core/logger.py`). Логируйте:

- ключевые действия пользователя (открытие папки, массовое удаление,
  редактирование метаданных);
- события синхронизации БД (сколько добавлено/обновлено, ошибки парсинга);
- миграции и восстановление БД;
- любые пойманные исключения, которые не приводят к падению приложения,
  но могут быть полезны для отладки.

Для ошибок, о которых должен узнать пользователь (не просто разработчик
из лога) — используйте `GalleryManager.error_occurred` (несёт
человекочитаемое сообщение), а не только `logger.error`. `MainWindow` уже
подписан на этот сигнал и показывает `QMessageBox.warning`.

## Тесты

**Начиная с этапа 5 дорожной карты рефакторинга ComfyUI Studio**
конфигурация pytest/ruff/mypy (и группа зависимостей `dev`) переехала
из локального `tools/promptvault/pyproject.toml` (удалён — слияние с
корневым, единая точка правды) в корневой `pyproject.toml` репозитория
ComfyUIStudio. Команды ниже запускаются из КОРНЯ репозитория (`cd`
туда, если вы внутри `tools/promptvault/`), а импортируемый пакет —
`comfyui_studio.promptvault`, а не `app` (переименован на этапе 2):

```bash
pip install -e ".[dev]"                    # из корня репозитория
pytest                                      # testpaths уже указывает на tools/promptvault/tests
pytest --cov=comfyui_studio.promptvault    # с покрытием
```

Новую логику в `comfyui_studio/promptvault/core/` (особенно всё, что
касается БД, миграций и фильтрации) крайне желательно сопровождать
тестами в `tools/promptvault/tests/`. Для тестов, работающих с БД,
используйте фикстуру `tmp_path` — не пишите тестовые данные в реальную
`~/.promptvault/promptvault.db`.

Тесты, требующие реального Qt-события (клики, сигналы виджетов), можно
гонять headless:

```bash
QT_QPA_PLATFORM=offscreen pytest
```

Фикстура `qapp` (единственный на тестовую сессию `QApplication`)
предоставляется плагином `pytest-qt`, а не определяется в проекте — он
же приносит `qtbot` для более сложных сценариев (ожидание сигналов и
т.п.), хотя пока в тестах используется только `qapp`.

**Осторожно с `QMenu.exec()`/`QDialog.exec()` в тестах** — это блокирующие
вызовы, ждущие реального взаимодействия пользователя, и зависают в
headless-окружении без возможности их закрыть программно (monkeypatch
класса тут не работает — `exec()` в PySide6 это скомпилированный
биндинг). Если нужно протестировать *содержимое* меню/диалога — выносите
его построение в отдельный метод без вызова `exec()` (см.
`GenerationList._build_context_menu`) и тестируйте этот метод напрямую,
а `contextMenuEvent`/аналоги оставляйте тонкой обёрткой, вызывающей
`exec()` только в реальном UI.

## Type hints, линтинг, статическая проверка типов

Публичные методы и функции должны иметь аннотации типов — как минимум
для параметров и возвращаемого значения. Приватные вспомогательные
функции внутри модуля — на усмотрение автора, но приветствуются.

Из корня репозитория (см. пояснение выше про перенос конфигурации в
корневой `pyproject.toml`):

```bash
ruff check comfyui_studio/promptvault          # линтинг + сортировка импортов (с --fix — автоисправление)
ruff format --diff comfyui_studio/promptvault  # доступен и настроен (см. корневой pyproject.toml), но НЕ
                                                # применяется автоматически и не входит в pre-commit — см. пояснение ниже
mypy comfyui_studio/promptvault/core           # статическая проверка типов, близкая к --strict
                                                # (пока только для core/ — ui/ ещё не полностью
                                                # типизирован, см. TODO.md)
```

`ruff format` **подключён и настроен** (`[tool.ruff.format]` в корневом
pyproject.toml), но **сознательно не применён** ко всему проекту и не
входит в pre-commit — у кода уже устоявшийся "разреженный" стиль с
осмысленными пустыми строками внутри функций, которые автоформаттер
агрессивно схлопывает (проверено: `ruff format --diff` на срез кода до
этого решения давал diff по всем 25 файлам, ~1330 удалённых строк).
Если когда-нибудь решите принять его стиль — прогоните `ruff format app`
на весь проект разом одним PR (разовая операция, не постепенное
внедрение), а не через pre-commit-хук исподтишка.

### pre-commit

```bash
pip install pre-commit
pre-commit install          # один раз — поставит git-хук
pre-commit run --all-files  # прогнать вручную на всём проекте
```

Хуки: `ruff --fix` (линт), `mypy app/core`, plus базовая гигиена
(trailing whitespace, missing final newline, merge conflict markers,
случайно закоммиченные большие файлы).

## Локализация (ru/en)

Каждая строка, которую видит пользователь в `app/ui/`, должна быть
обёрнута в `self.tr("...")` — это то, что позволяет переключать язык
интерфейса (см. `app/i18n.py`, переключатель — в `SettingsWindow`).
Исключения (сознательно НЕ оборачиваются):

- `logger.*(...)` — сообщения в лог пишутся для разработчика, не для
  пользователя интерфейса;
- бренд/версия (`"PromptVault"`, `f"PromptVault v{APP_VERSION}"`) —
  имя собственное, одинаково в любом языке;
- значения, одновременно используемые как текст ДЛЯ показа И как
  внутренний ключ сравнения (например, было `"Auto"/"CPU"/"GPU"` в
  `settings_window.py`) — перевод такого текста тихо сломал бы логику
  при сравнении `currentText() == "Auto"` после смены языка. Если
  нужно и показать переведённый текст, И сравнивать по значению —
  используйте `currentIndex()` вместо `currentText()` (см.
  `FilterPopup.favorites_only()`/`.model()`/`.sampler()` как пример) —
  так текст можно переводить свободно, не трогая логику.

Технические детали:

- Для строк с подстановкой (`f"Model: {x}"`) — `pyside6-lupdate`
  умеет извлекать для перевода только строковые ЛИТЕРАЛЫ, переданные
  в `self.tr(...)`, а не готовую f-строку. Пишите
  `self.tr("Model: {}").format(x)`, а не `self.tr(f"Model: {x}")`
  (второе просто не найдётся при сканировании).
- Тот же принцип для строк из словаря/enum-подобных ключей (например,
  `quality`/`speed` в `EMBEDDING_MODELS`, см. `app/config.py`) —
  `self.tr(some_dict[key])` не находится сканированием, нужен явный
  `if/elif` с литералами `self.tr("...")` на каждый вариант (см.
  `SettingsWindow._quality_label` как пример).
- Виджеты, которые пересоздаются заново при каждом показе (диалоги
  вроде `MetadataEditor`, контекстное меню в `GenerationList`) —
  подхватывают текущий язык автоматически, ничего дополнительно
  делать не нужно. Долгоживущие виджеты, построенные один раз при
  старте (`Toolbar`, `SettingsWindow`, `MainWindow`), — НЕ
  переводятся заново сами по себе при смене языка; для них нужен
  метод `retranslate_ui()`, который вызывающий код (см.
  `SettingsWindow._on_language_selected`) дёргает вручную после
  `LocalizationManager.apply_language(...)`.

Рабочий процесс после добавления/правки `self.tr(...)` в коде:

```bash
python -m tools.update_translations update    # .py -> .ts (мёржит,
                                                # не затирая уже
                                                # готовые переводы)
# вручную заполнить <translation> для новых строк в
# app/resources/translations/promptvault_ru.ts
python -m tools.update_translations compile    # .ts -> .qm
```

Коммитить нужно **и** `.ts` (редактируемый исходник перевода), **и**
`.qm` (то, что реально грузит `QTranslator` в рантайме, см.
`app/i18n.py`) — без пересборки `.qm` правки в `.ts` на запущенное
приложение не повлияют. CI (`i18n` job, см.
`.github/workflows/ci.yml`) проверяет через
`python -m tools.update_translations check`, что в `promptvault_ru.ts`
нет непереведённых строк — падает, если кто-то добавил `self.tr(...)`
и забыл прогнать `update`+перевести+`compile`.

`pyside6-lupdate`/`pyside6-lrelease` ставятся вместе с самим PySide6
через `pip install PySide6` (в `Scripts/` на Windows, в `bin/` на
Linux/macOS) — отдельно ставить не нужно, в отличие от того, что
предполагалось на момент первой версии этой инфраструктуры (см.
git-историю `app/i18n.py`).

## Стиль кода

- Docstring — на русском, в свободной форме, не Google/NumPy-style.
- Комментарии объясняют **почему**, а не **что** — код и так показывает что.
- Один файл — одна зона ответственности (см. структуру выше).
- Переменные-циклы вроде одиночной `l` избегать (легко спутать с `1`) —
  `ruff` (правило `E741`) на это ругается, называйте осмысленно
  (`lora`, `lora_data` и т.п.).
